Phase 5 · Step 2 · implemented 2026-11-17

The phone now keeps its own records

Before this step, the iPhone app's screens ran on a demo service that held fake patients in memory and forgot everything when the app closed. Step 2 replaces it with real Rust code that saves every action to a database file on the phone. It waits for the disk to confirm the save, and only then tells the screen it worked. Close the app, reopen it, and the shift is still there. No internet, login, or server is involved.

The big picture

What changed, in one picture

The phone now remembers

  • The shift: when it started, whether it's open. Ended shifts are kept.
  • The patient list in the order you added it, with room labels
  • Which patient is selected
  • Each patient's consent history, and the ambient or solo choice
  • Chart context you typed (history, meds, vitals and so on), with its source and whether it's been reviewed
  • Structured labs, imaging, vitals, meds, diagnoses and disposition
  • Templates and saved prompts, with every past version
  • A scratch draft per patient
  • Review, sign and plain-text export

It still can't

  • Record audio Step 4
    The rules are written and tested with a fake microphone. The real one is switched off.
  • Sync with the server Step 3
    Nothing is uploaded or downloaded. Nothing claims to be synced.
  • Write the HPI or MDM with AI Step 7
    The phone can display those sections when they arrive from the server. It has no code to create them.
  • Prove itself on Apple hardware needs the Mac
    Xcode build, simulator tests and a signed iPhone run haven't happened yet.

Layers

The path of one tap

Follow one action from start to finish: entering a potassium of 5.8 mmol/L for the patient in Room 4. It passes through three layers. Swift draws the screen, Rust makes the decisions, and SQLite holds the record.

  1. Swift

    1. The screen

    You fill in the lab form for Room 4 and tap Save. The form already holds Room 4's ID, so switching patients before you tap can't send the lab to the wrong chart.

    recordObjective( .lab("Potassium", 5.8, "mmol/L"), for: A) // A = Room 4
  2. Swift

    2. RustDeviceService

    Moves the job onto one background lane so the screen never freezes while the disk works. Jobs from the app run one after another, in order.

    DispatchQueue "app.ernote.rust-service" serial: one job at a time
  3. Bridge

    Generated bridge (UniFFI)

    Generated code converts Swift values into Rust values. Nobody edits it by hand. It's regenerated whenever the Rust interface changes, which is now at version 2.

    UUID → "0196c8e2-7a10-…" Double → f64 5.8 Swift and Rust versions must match
  4. Rust

    3. ErDevice: the inbox

    Drops the job into a queue that holds 64 jobs. If it's full, the call returns Busy right away. Once a job is accepted, the caller waits for the real answer. There's no timeout that could report failure while the save actually goes through.

    queue: 1 of 64 slots used full → Busy (try again)
  5. Rust

    4. DeviceCore: the checks

    One dedicated worker thread takes jobs one at a time. Before writing anything, it checks this one.

    ✓ Room 4 is on this shift ✓ Room 4's note isn't signed ✓ 5.8 is a real number (NaN or infinity is refused) ✓ time isn't >5 s in the future ✓ lab's patient = form's patient
  6. Disk

    5. SQLite: the save

    Adds one row to the events table and waits until the disk confirms it. If this fails, nothing below happens and the app gets a Storage error.

    events #1 ResultReceived · patient A synchronous = FULL
  7. Rust

    6. Update the in-memory note

    Only after the disk says yes does the core update its working copy of Room 4's note.

    note(A).results = [ "Potassium: 5.8 mmol/L" ]
  8. Swift

    7. Ring the bell, redraw

    The reply goes back to Swift with fresh screen data. Separately, a notification thread rings a bell that only says "something changed." It carries no patient data. Any screen that's listening re-reads what it shows and updates on the main thread.

    invalidated(revision: 12) → snapshot(), note(A) → MainActor redraw quick rings can merge into one

Analogy

The unit clerk at the nurses' station

One clerk
The owner thread. Every request goes through the same person, one at a time, so two requests can't collide.
An inbox tray with 64 slots
The bounded queue. When it's full you're told to come back (Busy). You're never left waiting forever.
Writes it in the binder first
SQLite. Nothing counts until it's written down and the ink is dry.
Rings a bell
The invalidation. The bell doesn't say what changed. Everyone just looks at the board again.
If the clerk faints mid-task
A Rust panic. The job returns Internal, the station closes, and the app has to reopen it. Nobody keeps working from a half-written page.

Storage

One file, two kinds of records

Everything lives in one SQLite file in the app's protected storage folder. Inside it, data takes two very different shapes. Which one a tap lands in tells you whether it's part of the clinical record.

Why two shapes?

The server already understands events like ResultReceived and AudioStarted, so Step 3 can upload them unchanged. Consent, chart context, templates and drafts have no server format yet. Rather than invent one now, Step 2 keeps them on the phone in device_state. Steps 3 and 7 will decide how they sync.

Every save to device_state names the revision it started from. The file accepts it only if that's still the latest revision, then bumps the number by one. That's how two edits can't silently overwrite each other.

Upgrading an older file

The table layout's version number is kept inside SQLite itself. A version 0 file (just events and snapshots, from earlier phases) gets the two new tables added in one transaction, and its old events are left alone. If anything about the upgrade looks wrong, such as a table with the wrong columns, the whole upgrade rolls back.

A file written by a newer app version is refused rather than guessed at. The JSON inside device_state has its own version number (format_version: 1) for the same reason.

    Capture and consent

    Recording: rules built, microphone off

    The production app can't record. RustDeviceService reports supportsRecording = false, never asks for microphone permission, and opens the Rust core with a mic adapter that's always unavailable. The rules for when recording is allowed are still written and tested now, using a fake microphone in Rust tests. Step 4 then only has to plug in real hardware.

    Six checks before the mic can start

    1. Is a shift open?no → refused
    2. Is this the selected patient?You can't start recording for a patient you aren't on.no → refused
    3. Is the note at Registered, Idle or Finalizing?Pending sign-off and Signed notes can't record. A Finalizing re-eval keeps the existing MDM.no → refused
    4. Is a microphone adapter available?Production phone: no. Rust tests: a fake one.no → refused
    5. Is nothing else recording, interrupted or waiting on a stop?no → refused
    6. Ambient only: is the latest consent Granted?Unknown, Declined and Revoked all fail. Solo dictation skips this check, but only if the clinician chose solo on purpose. Declining never switches modes by itself.no → refused

    All six pass: the mic starts, then AudioStarted and the new segment's details (mode, source, which consent revision allowed it) save together in one transaction. If that save fails, the mic is released immediately.

    Changing consent to anything other than Granted stops the mic before trying to save the change. If that save then fails, ambient stays locked for that visit until a Granted choice saves successfully.

    Safety

    When something goes wrong

    Most of the Step 2 code is about failure. The rule throughout is to never report success for something that isn't on disk, and never invent data to fill a gap.

    The form outlives the selection

    saved to Room 4

    The lab form is open for Room 4. You tap Hall 3, then tap Save on the form.

    The lab is written to Room 4. Hall 3 is untouched. A lab for an unknown or signed visit is refused before anything is written.

    Every command names its patient. The core never looks at "who's selected" to decide where data goes.

    Two edits of the same item

    Conflict

    A context item is at version 3. An older screen still shows version 2 and saves its copy.

    The save is refused. Version 3 stays. The screen keeps the unsaved text so nothing typed is lost.

    Each save says which version it started from. If that isn't the latest, it doesn't overwrite.

    Stop worked, switch failed

    Storage

    Recording A1 for Room 4, you tap Hall 3. The mic stops and the stop saves. Saving "selected = Hall 3" then fails.

    You see an error. Room 4 is still selected and shows Paused. Retrying selects Hall 3 without a second stop or restarting the mic.

    These are two saves, and the code reports them as two. It doesn't pretend they're one atomic action.

    App killed while recording

    Interrupted

    AudioStarted for A2 saved, then the phone died.

    On reopen, Room 4 shows Interrupted and recording is blocked. The core doesn't stretch the end time to "now," write a transcript, or turn the mic on.

    A real process-kill test covers this. Step 4 will close the segment using the audio file's real end.

    A stop can't be saved

    PendingStop

    The mic turns off, but the disk refuses the AudioStopped write.

    Other changes are blocked until a retry saves that same stop, with the same event ID and contents.

    Reusing the ID means a retried stop can never be counted twice.

    Consent revoked, disk failing

    mic stopped first

    The patient revokes consent mid-recording, and the consent save fails.

    The mic stopped before the save was tried. Ambient stays locked for that visit until a Granted choice saves.

    Safety comes before storage: stopping the mic doesn't wait on the disk.

    Disk full

    Storage

    You add Hall 5 and the save fails because the disk is full.

    Hall 5 doesn't exist anywhere, not even in memory. The roster is exactly what's on disk.

    A test fills a real SQLite file to prove the rollback.

    A second opener

    Busy

    Something tries to open the same database file while the core has it, even through a different path or a link to it.

    It's refused. Only one core can have a live copy of the data in memory.

    An operating-system file lock is held for the core's whole lifetime. SQLite's own lock wouldn't be enough.

    Wrong account

    Scope

    The file belongs to synthetic-development. Someone opens it as a different account.

    It's refused before any data is read.

    This keeps local data separated by account. It isn't server authorization, which comes with real login.

    The boundary

    What the screen gets back

    Swift never sees raw events or Rust's internal objects. It gets flat summaries built for display. Here's Room 4's note view at the end of the walkthrough.

    note(A) → NoteViewwhat Swift receives

    When something fails, Swift gets one of ten fixed error names. None of them carry SQL, file paths, patient text or prompt text, so nothing sensitive can end up in a phone log.

    ErrorMeans
    InvalidInputA bad value: NaN, text too long, a time in the future
    InvalidStateNot allowed right now, such as recording a patient you aren't on
    NotFoundNo such patient or item on this device
    ConflictSomeone saved a newer version first, or a shift is already open
    ScopeThe file belongs to a different account
    StorageThe disk refused: read-only, locked or full
    RecoveryThe saved data doesn't add up and needs attention
    ClosedThe core was already shut down
    BusyThe queue is full, or another opener holds the file
    InternalA bug or crash. The core shuts itself down.

    Around the edges

    Other changes, and what's still open

    Changes outside the phone code

    • Shared app logic (er-app) now has a setting for who writes the AI text. The CLI keeps doing it locally. The phone build leaves the AI code out entirely, and a dependency check fails the build if the AI client or HTTP library sneaks in.
    • Event publishing: a retried stop reuses its original event ID, so it can't be applied twice.
    • Storage (er-store): the layout version and upgrade described above, plus safer write settings for SQLite. Resending an event with the same ID returns its original sequence number. Resending the same ID with different contents is rejected.
    • Swift: the real service now runs in both Debug and Release builds. Demo controls appear only with the demo service. Failed text drafts stay on screen, and screens show where data came from and mark audio, AI and EMR as unavailable.
    • Unchanged: the server API, OpenAPI file and AWS resources.

    Still open

    • Apple acceptance. This Linux machine has no Xcode. On the M1, run scripts/check-bridge-apple.sh to build the Apple binaries with SQLite bundled in and run simulator tests. Then do the physical drill: two visits, consent, context and a preference, force-quit, relaunch, confirm it all came back. Record the result in docs/ops/ios-development.md.
    • Step 3 (next): sync. Step 3 adds syncing alongside this file without replacing it:
      • keep a durable outbox of events not yet sent
      • link local shift S1 to the server's shift ID
      • register patients before their events, using the same IDs
      • download server events in server order, then replay any unsent local ones on top
      • decide how consent, context, templates and drafts sync
      • stay inside the 60 requests per minute limit

    Jargon decoder

    Terms from the implementation doc, in plain words.

    Doc saysPlain English
    composition rootThe one place that wires the existing pieces (store, event bus, note loader) into a working whole. Here that's the new er-device crate.
    UniFFIThe tool that generates the Swift ↔ Rust translation code from the Rust definitions.
    owned UniFFI object, handle (ErDevice)The single object Swift holds to use the Rust core. Swift holds it, and Rust controls everything inside it.
    owner thread, serialized ownerThe one Rust thread allowed to touch the core and the database. Everything is done in order, one job at a time.
    bounded admissionThe job queue has a fixed size (64). When it's full you get Busy.
    persist-first, acknowledged writeSave to disk, wait for the confirmation, then update memory and report success.
    event, event-sourcedEach clinical action is saved as a "this happened" row. The note is whatever you get by playing those rows back in order.
    projectionThe in-memory note built from those events. It's a view of the events, not a second copy of the truth.
    replay, rehydrateRebuilding a note by re-applying its saved events, starting from a snapshot checkpoint if one exists.
    snapshotA saved checkpoint of a note, so reopening doesn't replay every event. A damaged one is thrown away and rebuilt.
    metadata aggregateThe single JSON document in device_state.
    compare-and-save, CAS, expected revision/versionA save names the version it started from. If the stored version has moved on, the save is refused with Conflict.
    metadata revision vs projection versionTwo separate counters. One counts saves to device_state. The other counts changes to one patient's note.
    full invalidation, coalescedOne generic "something changed" bell. Several quick changes can merge into one ring. Screens re-read everything they show.
    read model, DTO, viewPlain, flat data shapes made for the screen, like NoteView.
    scopeA label for which account owns the database file. The placeholder synthetic-development is used until real login exists.
    user_version, format_versionTwo version stamps. One is for the table layout and the other for the JSON layout inside device_state.
    WAL, synchronous = FULLSQLite settings that put "never lose a confirmed save" ahead of speed.
    UUIDv7Unique IDs that begin with a timestamp, so they sort by when they were made. They're made on the phone and will be reused when syncing.
    segment, encounterOne stretch of recording. Pausing ends a segment and resuming starts a new one in the same visit.
    boundaryThe confirmed time a recording segment started or stopped.
    server-owned generationTranscripts, HPI and MDM are written by the server worker and delivered to the phone. The phone never writes them.
    fixture serviceThe demo service with fake in-memory patients. It's now only used for previews.
    panic containment, faultedIf Rust code crashes inside a job, that job returns Internal and the core shuts down instead of carrying on in an unknown state.
    MainActorSwift's main UI thread, where screen updates happen.
    interface version 2The bridge's version number. The Swift bindings and the Rust library must match it exactly.
