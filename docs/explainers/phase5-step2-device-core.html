The big picture

The pieces that exist now

Before Phase 5 the screens ran on a demo service that held fake patients in memory and forgot them when the app closed. Now each tap crosses the bridge into Rust and is saved on the phone. A separate Rust thread trades records with the server. The one missing piece on the phone is the Swift recorder that produces audio files.

The phone can now

  • Keep the shift, roster, selection, consent history, chart context, templates and drafts through a force-quit Step 2
  • Save labs, imaging, vitals, meds, diagnoses and disposition as clinical events Step 2
  • Upload those events when a connection appears, without duplicates, and download the server's events in the server's order Step 3
  • Show the HPI the server worker wrote, once it arrives through sync Step 3
  • Send consent and recording records to the server so a second phone can pick up the shift Step 3
  • Check, upload and later delete audio chunk files, and close a crashed recording at the last chunk it holds Step 4

It still can't

  • Record from the microphone Step 4, Mac half
    The Rust side is ready for files. The Swift recorder and its bridge calls aren't written.
  • Sign in with a real account Step 5
    Sync works with development tokens. Cognito sign-in is part of the full screens.
  • Ask for an MDM or apply a template Step 7
    The phone shows server-written sections. It can't request generation yet.
  • Run on the watch or lock screen Step 6
  • Prove itself on a real iPhone needs the Mac
    CI builds and runs simulator tests now. No signed install has happened.

Layers

The path of one tap

Follow one action from start to finish: entering a potassium of 5.8 mmol/L for the patient in Room 4. It passes through three layers. Swift draws the screen, Rust makes the decisions, and SQLite holds the record.

  1. Swift

    1. The screen

    You fill in the lab form for Room 4 and tap Save. The form already holds Room 4's ID, so switching patients before you tap can't send the lab to the wrong chart.

    recordObjective( .lab("Potassium", 5.8, "mmol/L"), for: A) // A = Room 4
  2. Swift

    2. RustDeviceService

    Moves the job onto one background lane so the screen never freezes while the disk works. Jobs from the app run one after another, in order.

    DispatchQueue "app.ernote.rust-service" serial: one job at a time
  3. Bridge

    Generated bridge (UniFFI)

    Generated code converts Swift values into Rust values. Nobody edits it by hand. It's regenerated whenever the Rust interface changes. It's at version 3 now, since Step 3 added sync.

    UUID → "0196c8e2-7a10-…" Double → f64 5.8 Swift and Rust versions must match
  4. Rust

    3. ErDevice: the inbox

    Drops the job into a queue that holds 64 jobs. If it's full, the call returns Busy right away. Once a job is accepted, the caller waits for the real answer. There's no timeout that could report failure while the save actually goes through.

    queue: 1 of 64 slots used full → Busy (try again)
  5. Rust

    4. DeviceCore: the checks

    One dedicated worker thread takes jobs one at a time. Before writing anything, it checks this one.

    ✓ Room 4 is on this shift ✓ Room 4's note isn't signed ✓ 5.8 is a real number (NaN or infinity is refused) ✓ time isn't >5 s in the future ✓ lab's patient = form's patient
  6. Disk

    5. SQLite: the save

    Adds one row to the events table and waits until the disk confirms it. Since Step 3, the same write adds the event's delivery row, so the courier will send it later. If this fails, nothing below happens and the app gets a Storage error.

    events #1 ResultReceived · patient A delivery: E1 → waiting to send synchronous = FULL
  7. Rust

    6. Update the in-memory note

    Only after the disk says yes does the core update its working copy of Room 4's note.

    note(A).results = [ "Potassium: 5.8 mmol/L" ]
  8. Swift

    7. Ring the bell, redraw

    The reply goes back to Swift with fresh screen data. Separately, a notification thread rings a bell that only says "something changed." It carries no patient data. Any screen that's listening re-reads what it shows and updates on the main thread.

    invalidated(revision: 12) → snapshot(), note(A) → MainActor redraw quick rings can merge into one

Analogy

The unit clerk at the nurses' station

One clerk
The owner thread. Every request goes through the same person, one at a time, so two requests can't collide.
An inbox tray with 64 slots
The bounded queue. When it's full you're told to come back (Busy). You're never left waiting forever.
Writes it in the binder first
SQLite. Nothing counts until it's written down and the ink is dry.
Rings a bell
The invalidation. The bell doesn't say what changed. Everyone just looks at the board again.
If the clerk faints mid-task
A Rust panic. The job returns Internal, the station closes, and the app has to reopen it. Nobody keeps working from a half-written page.

Storage

One file, one folder

Everything the phone keeps lives in one SQLite file in the app's protected storage folder, plus a sibling folder for audio chunks. Step 2 created the file. Steps 3 and 4 each added tables without touching the old ones. Which table a record lands in tells you whether it's part of the clinical record.

Why two shapes?

The server already understands events like ResultReceived and AudioStarted, so Step 3 uploads them unchanged. Consent and recording attribution got their own small server contract in Step 3. Chart context, templates and drafts still have no server format, so they stay in device_state on the phone, and the screen labels them local-only. Step 7 decides how they reach the server.

Every save to device_state names the revision it started from. The file accepts it only if that's still the latest revision, then bumps the number by one. That's how two edits can't silently overwrite each other.

Upgrading an older file

The layout version lives inside SQLite itself. An older file is upgraded one version at a time, each in a single transaction: 0 → 1 adds the Step 2 tables, 1 → 2 adds sync and creates delivery rows for existing events with their original IDs, 2 → 3 adds the chunk ledger. Old events are never rewritten. If anything looks wrong, such as a table with the wrong columns, that upgrade rolls back.

A file written by a newer app version is refused rather than guessed at. The JSON in device_state and the sync bookkeeping each carry their own format version for the same reason.

    Capture and consent

    Recording: rules built, microphone still off

    The production app can't record yet. RustDeviceService reports supportsRecording = false, never asks for microphone permission, and opens the Rust core with a mic adapter that's always unavailable. The rules for when recording is allowed were written and tested in Step 2 using a fake microphone. Step 4 added everything Rust does with the files a recorder produces, tested with a fake recorder that writes real files. The Swift recorder that plugs into this is the remaining Mac work.

    Six checks before the mic can start

    1. Is a shift open?no → refused
    2. Is this the selected patient?You can't start recording for a patient you aren't on.no → refused
    3. Is the note at Registered, Idle or Finalizing?Pending sign-off and Signed notes can't record. A Finalizing re-eval keeps the existing MDM.no → refused
    4. Is a microphone adapter available?Production phone: no. Rust tests: a fake one.no → refused
    5. Is nothing else recording, interrupted or waiting on a stop?no → refused
    6. Ambient only: is the latest consent Granted?Unknown, Declined and Revoked all fail. Solo dictation skips this check, but only if the clinician chose solo on purpose. Declining never switches modes by itself.no → refused

    All six pass: the mic starts, then AudioStarted and the new segment's details (mode, source, which consent revision allowed it) save together in one transaction, and the recorder is handed its audio folder. If that save fails, the mic is released immediately.

    Changing consent to anything other than Granted stops the mic before trying to save the change. If that save then fails, ambient stays locked for that visit until a Granted choice saves successfully.

    Step 3 · implemented 2026-11-17

    Sync: getting the phone and the server to agree

    Step 3 adds a courier who works beside the unit clerk. The clerk (the core's owner thread) keeps taking local changes. The courier (the sync worker, on its own thread) carries saved records to the server, brings the server's records back, and hands every reply to the clerk. The courier never edits the clinical record itself. A network failure never empties the phone's file or switches it to demo data.

    Three things that sound alike

    The outgoing tray

    outbox

    A delivery row points at an event already saved on the phone. Retrying sends the same event with the same ID. It never creates a second event or a second patient.

    Created in the same write as the event itself.

    A receipt

    acknowledgment

    The server says "I stored E1 at position 204." That proves the server has E1. It doesn't prove the phone has read everything that came before it.

    Saving a receipt never moves the bookmark.

    The bookmark

    cursor

    The phone has safely stored the server's history through position 204. The page and the new bookmark are written in one transaction: both succeed or neither does.

    "Up to date" requires an empty tray and a bookmark past every receipt.

    Follow the Room 4 potassium to the server

    1. Phone

      1. Saved offline

      The lab from the tap above is saved as event E1. The same write adds its delivery row. Without a connection it just waits.

      events #1 ResultReceived(A) delivery: E1 → waiting to send
    2. Courier

      2. Check who's asking

      The courier gets an access token from the platform and asks the server who it belongs to. Clinical data goes nowhere until that matches the account bound to this file.

      token ← platform sign-in GET /v1/me ✓ org + clinician match
    3. Server

      3. Shift, then patient

      The phone made shift L1 offline. The server makes its own shift ID, so the phone asks for the active shift first and saves the mapping. Patient A is registered with the same ID before any of A's events go up.

      GET /v1/shifts/active → S9 local L1 ↔ server S9 register patient A (same ID)
    4. Server

      4. Read before writing

      The courier reads A's new server history first. That's how it would learn the note was signed elsewhere, before uploading something that no longer fits.

      GET …/A/events?since=0 ✓ not signed · E1 still fits
    5. Server

      5. Send the original E1

      Same ID, same body. A batch stays under 500 events and just under the server's 2 MiB limit.

      POST …/A/events [E1] ← receipt: E1 = position 204
    6. Phone

      6. Save the receipt

      E1 is now known to be on the server. The bookmark stays where it was.

      E1: receipt 204, not confirmed bookmark: still 0
    7. Phone

      7. Read it back, rebuild

      The next page includes E1 with the same body. The phone saves the page and moves the bookmark in one transaction, rebuilds A's note in server order, and rings the bell.

      page ← …, 204 (E1) bookmark: 0 → 204 queued 0 · awaiting 0 · up_to_date

    When a reply disappears

    The hard case isn't "the internet is off." It's "the server saved something, but the phone never heard back." Say a batch holds E1, E2 and E3, and the server saves E1 before failing.

    MomentPhone knowsNext
    Before the batchE1, E2, E3 waitingSend all three
    Reply lostUnsure about all threeWait, then read history
    History shows E1E1 confirmed; E2, E3 waitingSend E2 and E3
    Both confirmedThree events, no duplicatesNormal polling

    A test makes the real server save only the first event, then swaps its reply for an error. Both sides end with exactly three events.

    The server's order wins

    The phone may insert events in a different order than the server keeps them, for example when a transcript downloads after a local lab. The note is rebuilt in server order, then any still-unsent local events go on top.

    EventPhone insertedServer position

    Rebuilt order: E1 → E2 → E3. The Step 2 snapshot shortcut assumed phone order, so once sync starts the core rebuilds from events instead.

    Staying under the server's request limit

    Consent and recording records get their own contract

    Consent was phone-only in Step 2. Step 3 adds a separately versioned server endpoint, /v1/patients/{id}/capture-audit/v1, holding two histories per visit: consent choices, and recording segments with their mode, source device and the consent revision that allowed them.

    • The server takes the organization and clinician from the login, never from the request.
    • Past consent entries can't be rewritten. A segment's attribution can't be relabeled, and its end time can be set once.
    • Each segment must match the patient's real AudioStarted and AudioStopped events, so one visit's segment can't be filed under another.
    • A second phone reads clinical history first, then adopts consent and segments. It never starts a microphone.

    When the connection misbehaves

    What happenedWhat the phone does
    No response, or a 5xxKeeps the work, waits longer each time, up to a minute
    401Asks the platform for a fresh token once, then re-checks membership
    403Shows a sign-in problem rather than "offline"
    404Shows "not found" and never invents a new patient ID
    429Waits as told, between 60 seconds and one day
    409Keeps the pending work and re-reads; real conflicts go to review
    Wrong org, clinician or serverRefuses before sending any clinical data

    Wait times survive a restart. Production builds require HTTPS. Plain HTTP exists only in a test feature that production packaging rejects.

    Step 4 · Rust half implemented 2026-11-18

    Audio: files the phone can trust

    A segment is one stretch of recording for one patient, from a start to a pause, a patient switch, a consent change or the end of the shift. The recorder cuts it into chunks of about 30 to 60 seconds. Rust never touches the microphone. It takes each finished chunk file, checks it, numbers it, uploads it once the server knows about the recording, and deletes it after the server's transcript comes back.

    The hand-off is a rename

    When a segment starts, the core gives the recorder a folder next to the database. The recorder writes each chunk under a temporary name ending in .partial. When the encoder has finished and flushed the file, it renames it to a fixed pattern. That rename is the hand-off. No audio and no file path crosses the bridge as an argument.

    0198f1c0-…-7000segment ID_ 2position_ 1794970920000audio start, ms_ 1794970932000audio end, ms. m4awav, m4a, ogg or mp3

    This one is the third chunk of a segment: 12 seconds of audio ending at 10:02:12 PM. The core reads the name only in this exact spelling. Anything else is left alone and counted as unclaimed.

    Why a folder instead of a function call? A chunk can finish at the same moment the clinician taps pause. If Swift had to call into Rust to deliver it, that call would queue behind the pause, and the pause is waiting for the recorder to stop. With a folder there's nothing to wait for. The recorder renames its last file before stop() returns, and the core scans right after.

    Five rules the recorder must follow

    • A new segment ID for every start. Never reuse one.
    • Positions start at 0, go up by one, and are renamed in that order.
    • Times are the audio's own capture clock, not file times.
    • stop() returns only after every chunk, including the short last one, is renamed.
    • Never touch a file after renaming it.

    What Rust decides, not Swift

    • Which chunk is final. If the app is killed, Swift never gets to say "that was the last one," so Rust decides the same way every time: the highest-numbered accepted chunk when the segment closes.
    • The upload number. Accepted chunks get server numbers 0, 1, 2 with no gaps, so the server's assembly can't stall waiting for a number that will never come.
    • When a gap is permanent. While recording, the core waits at a missing position. Once the segment has stopped, the gap is counted as a missing chunk.

    Checks before the core takes a file

    1. Is it a real file?A symlink is refused.not_a_file
    2. Is it non-empty and at most 16 MiB?16 MiB is the server's upload limit.chunk_empty · chunk_too_large
    3. Is it a complete file of the type it claims?WAV needs its header and data. M4A needs its index (moov), which a killed encoder usually never writes.container_mismatch
    4. Does it fit inside its segment?Not before the start or after the stop, with two seconds of slack between the tap and the audio clock.outside_segment
    5. Does it start after the previous chunk ends?overlaps_previous
    6. Is it five minutes or shorter?chunk_too_long
    7. Is the segment still open?A file that arrives after its segment closed is never added to it. That's how a revocation or a patient switch stays a hard boundary.late_chunk

    All pass: the core hashes the file (SHA-256), gives it the next upload number and adds a queued row to the chunk ledger. A refused file keeps its reason in the ledger and stays on disk, so nothing disappears silently.

    After a crash

    When audio is deleted: the server writes TranscriptReady for a segment only after every chunk has been transcribed. Step 9 can choose to keep audio longer; the rule lives in one function.

    Safety

    When something goes wrong

    Most of the Phase 5 Rust code is about failure. Two rules hold throughout: never report success for something that isn't on disk, and never invent data to fill a gap. Steps 3 and 4 add a third: a retry reuses the original identity, so nothing is counted twice.

    Step 2

    The form outlives the selection

    saved to Room 4

    The lab form is open for Room 4. You tap Hall 3, then tap Save on the form.

    The lab is written to Room 4 and Hall 3 is untouched. A lab for an unknown or signed visit is refused before anything is written.

    Every command names its patient. The core never uses "who's selected" to decide where data goes.

    Step 2

    Two edits of the same item

    Conflict

    A context item is at version 3. An older screen still shows version 2 and saves its copy.

    The save is refused and version 3 stays. The screen keeps the unsaved text so nothing typed is lost.

    Each save names the version it started from. If that isn't the latest, it doesn't overwrite.

    Step 2

    Stop worked, switch failed

    Storage

    Recording for Room 4, you tap Hall 3. The stop saves. Saving "selected = Hall 3" then fails.

    You see an error. Room 4 is still selected and shows Paused. Retrying selects Hall 3 without a second stop.

    These are two saves, and the code reports them as two.

    Step 2

    A stop can't be saved

    PendingStop

    The mic turns off, but the disk refuses the AudioStopped write.

    Other changes are blocked until a retry saves that same stop, with the same event ID and contents.

    Reusing the ID means a retried stop can never be counted twice.

    Step 2

    Consent revoked, disk failing

    mic stopped first

    The patient revokes consent mid-recording, and the consent save fails.

    The mic stopped before the save was tried. Ambient stays locked for that visit until a Granted choice saves.

    Stopping the mic doesn't wait on the disk.

    Step 2

    A second opener, or the wrong account

    Busy · Scope

    Something else opens the same file while the core holds it, or opens it as another account.

    Both are refused before any data is read. Only one core can hold the data in memory.

    An operating-system file lock is held for the core's whole lifetime.

    Step 3

    The server saved it, the reply was lost

    no duplicates

    A batch of E1, E2 and E3 goes up. The server stores E1, then the connection drops.

    The phone reads the server's history, finds E1, and sends only E2 and E3, with their original IDs.

    If an accepted ID is resent anyway, the server returns its original position and stores nothing new.

    Step 3

    Signed elsewhere while offline

    needs review

    Room 4's note is signed from another device. This phone, offline, has a pending lab for Room 4.

    On reconnect the lab is not uploaded or folded into the signed note. It shows as a conflict until someone discards it.

    Reads come before writes, so the phone learns about the signature first.

    Step 3

    The shift-start reply was lost

    one shift

    The server created shift S9, but the phone never got the answer.

    Next time, the phone asks for the active shift, finds S9 and maps its local shift to it. It never starts a second one.

    The phone doesn't assume a timed-out request did nothing.

    Step 4

    The app dies mid-chunk

    Interrupted

    Two chunks were handed over. The third was still a .partial file when the phone died.

    On reopen the segment closes at the end of chunk #1, which becomes final. The partial file is counted and never uploaded.

    The core never stretches a recording to "now" or guesses an end time.

    Step 4

    An M4A with no index

    container_mismatch

    A killed encoder leaves a renamed .m4a whose index was never written.

    The core refuses it and records why. The file stays on disk and nothing broken is uploaded.

    The audio in that file is lost, which is why the Mac work must check how the encoder fails.

    Step 4

    A chunk after the pause

    late_chunk

    A file for Room 4's segment appears after the clinician paused and switched to Hall 3.

    It's refused. Nothing is ever added to a closed segment, so audio can't drift across a patient or pause boundary.

    Consent revocation closes a segment the same way.

    Decisions waiting on you

    A recording with no usable audio

    blocks the note

    If the mic captured nothing, or every file was refused, the server never writes a transcript for that segment, and the note can't reach review. Options: a server-side "no audio captured" marker, or uploading generated silence, which means sending fake audio.

    A chunk refused after the server knows it

    stalls assembly

    The server waits for every chunk number before assembling a transcript, and has no way to be told one is lost. The suggestion is a small server call that marks a chunk lost, so assembly continues with a visible gap.

    Uploading while still recording

    uploads wait

    Step 3 blocks sync while the mic is on, so audio uploads after a pause. An hour of one-minute chunks is about 120 API calls, a few minutes under the 30-per-minute audio limit. Allowing audio-only sync during recording would remove the wait.

    The CI security job

    fails

    It fails only on advisory RUSTSEC-2026-0459 in libsqlite3-sys, the SQLite library the phone uses. Upgrading is blocked by sqlx's pinned version. Choose a time-boxed exception or wait for sqlx. The existing rsa exception expires 2026-11-20.

    Jargon decoder

    Terms from the implementation doc, in plain words.

    Doc saysPlain English
    composition rootThe one place that wires the existing pieces (store, event bus, note loader) into a working whole. Here that's the new er-device crate.
    UniFFIThe tool that generates the Swift ↔ Rust translation code from the Rust definitions.
    owned UniFFI object, handle (ErDevice)The single object Swift holds to use the Rust core. Swift holds it, and Rust controls everything inside it.
    owner thread, serialized ownerThe one Rust thread allowed to touch the core and the database. Everything is done in order, one job at a time.
    bounded admissionThe job queue has a fixed size (64). When it's full you get Busy.
    persist-first, acknowledged writeSave to disk, wait for the confirmation, then update memory and report success.
    event, event-sourcedEach clinical action is saved as a "this happened" row. The note is whatever you get by playing those rows back in order.
    projectionThe in-memory note built from those events. It's a view of the events, not a second copy of the truth.
    replay, rehydrateRebuilding a note by re-applying its saved events, starting from a snapshot checkpoint if one exists.
    snapshotA saved checkpoint of a note, so reopening doesn't replay every event. A damaged one is thrown away and rebuilt.
    metadata aggregateThe single JSON document in device_state.
    compare-and-save, CAS, expected revision/versionA save names the version it started from. If the stored version has moved on, the save is refused with Conflict.
    metadata revision vs projection versionTwo separate counters. One counts saves to device_state. The other counts changes to one patient's note.
    full invalidation, coalescedOne generic "something changed" bell. Several quick changes can merge into one ring. Screens re-read everything they show.
    read model, DTO, viewPlain, flat data shapes made for the screen, like NoteView.
    scopeA label for which account owns the database file. The placeholder synthetic-development is used until real login exists.
    user_version, format_versionTwo version stamps. One is for the table layout and the other for the JSON layout inside device_state.
    WAL, synchronous = FULLSQLite settings that put "never lose a confirmed save" ahead of speed.
    UUIDv7Unique IDs that begin with a timestamp, so they sort by when they were made. They're made on the phone and will be reused when syncing.
    segment, encounterOne stretch of recording. Pausing ends a segment and resuming starts a new one in the same visit.
    boundaryThe confirmed time a recording segment started or stopped.
    server-owned generationTranscripts, HPI and MDM are written by the server worker and delivered to the phone. The phone never writes them.
    fixture serviceThe demo service with fake in-memory patients. It's now only used for previews.
    panic containment, faultedIf Rust code crashes inside a job, that job returns Internal and the core shuts down instead of carrying on in an unknown state.
    MainActorSwift's main UI thread, where screen updates happen.
    interface version 3The bridge's version number. The Swift bindings and the Rust library must match it exactly. Step 3 raised it from 2; Step 4 didn't change it.
    XCFrameworkThe packaged Rust library Xcode links, with one build for real iPhones and one for the Apple-silicon simulator.
    outbox, delivery rowThe outgoing tray: one row per saved event that still has to reach the server.
    acknowledgment, receiptThe server's reply naming the position where it stored an event. Proof the server has it, not proof the phone is up to date.
    cursorThe download bookmark: how far through the server's history the phone has safely stored.
    server order, pending tailRebuild a note using the server's positions first, then the phone's unsent events in the order they were made.
    request budget, Retry-AfterThe phone's own cap of 48 requests a minute, and the server's "try again in N seconds" instruction.
    capture auditThe versioned server record of consent choices and recording segments for one visit.
    chunk, position, indexA 30–60 second piece of one segment. Position is the recorder's number for it; index is the gap-free upload number the core assigns.
    sealing, final chunkClosing a segment once it stops. Its highest-numbered accepted chunk is marked final, and nothing can be added afterwards.
    chunk ledgerThe device_audio_chunks table: what the core knows about each chunk file, without the audio.
    presigned URLA short-lived upload address that works like a one-time password. Kept in memory only.
    container check, moovMaking sure a file is complete for its type. moov is the index at the end of an M4A that a killed encoder never writes.
    TranscriptReadyThe server event saying a segment's chunks were all transcribed and assembled. Its arrival is what lets the phone delete the audio.
    echo transcriber, RustFS, ElasticMQTest stand-ins: a transcriber that reads back the words planted in a WAV, local object storage, and a local job queue.
