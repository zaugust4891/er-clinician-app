infra/ · Terraform · Phase 4 Step 8

The cloud setup, from the top down

infra/ is Terraform code: text files that describe every AWS resource the server needs, from the private network and database to the load balancer, permissions and alarms. Running Terraform compares that description with what exists in AWS and creates or changes things to match. Almost all of it is written and tested offline but has not been created in AWS yet. Only the bootstrap layer, which stores Terraform's own records, is live.

    Level 2 · how the code is organized

    Five roots, three layers

    A root is a folder you run Terraform in. Each one keeps its own state file, so each can be given its own permissions and can break without taking the others with it. There are five: one bootstrap, then a foundation and a release for each environment.

    Why split foundation from release?

    A deploy happens often and should only be able to do one thing: swap the running containers. A foundation change is rare, reviewed, and can delete a database. Keeping them in separate roots means a routine deploy never carries the power to touch the database.

    It also avoids a fight. If the deploy script registered containers on its own while Terraform also described them, Terraform's next run would try to undo the deploy. Here the release root owns the container definitions, and the pipeline just hands it the new image digest.

    Why a manifest file instead of reading the foundation's state?

    Terraform can read another root's state directly, but that hands over everything in it, including values that are only stored there because Terraform had to remember them. The manifest is an explicit list of names. The release's permissions can be limited to that one file, and secrets never appear in it, only pointers to them.

    Level 3 · drill down

    Each part, in order of what depends on what

    Example values are realistic but synthetic. The account ID is shown as 000000000000, the project prefix is ernote, and the environment is staging, so most names start with ernote-staging-.

    records

    Bootstrap

    infra/bootstrap/

    Terraform needs somewhere safe to keep its state before it can build anything else, so this root goes first and is run by hand once per account. It is the only part that exists in AWS today.

    State bucket
    ernote-tfstate-000000000000-us-east-2. Versioned, so every old state is recoverable for 365 days. Can't be deleted by Terraform.
    Deploy bucket
    ernote-deploy-…. Holds each environment's manifest and the pipeline's release records. Old versions kept 180 days.
    KMS key
    alias/ernote-tfstate. Encrypts both buckets, rotates yearly, 30-day deletion delay. Usable only through S3 in this region.
    Locking
    Terraform writes a small .tflock file next to the state. A second person running the same root at the same time is refused. No DynamoDB table needed.
    Bucket rules
    Refuse plain HTTP, TLS older than 1.2, and uploads with the wrong encryption. These apply even to an account admin.
    GitHub trust
    An optional sign-in link so GitHub Actions can get short-lived AWS credentials. Off until GitHub environments are protected.

    Five roles, each fenced to one state file

    Each root gets its own IAM role. The role can read and write its own state file and lock, read its environment's manifest, and (for foundations) publish it. It then carries an explicit Deny on every other root's files. In IAM, a Deny beats any Allow, so even if someone attaches a broader policy to the role by mistake, a staging credential still can't touch production state.

    network

    Network

    infra/modules/network/

    The VPC is a private address range, 10.40.0.0/16 (65,536 addresses). The module cuts it into eight equal slices of 8,192 addresses. Six are used, in pairs, so every tier exists in both availability zones (two separate data centers in the region). Two are kept free for later.

    Door rules (security groups)

    Every component gets its own security group, and only these connections are allowed. Everything else is refused, including the VPC's default group, which is emptied on purpose.

    FromToPort
    Listed client IPs (empty for now)Load balancer443
    Load balancerAPI8443
    API, worker, migration, onboardingPostgreSQL5432
    Each taskAnywhere, HTTPS only443

    Never created: task-to-task traffic, SSH, a jump box, or any path from the internet to the database.

    Shortcuts and trade-offs

    • S3 gateway endpoint. A free private shortcut from the task subnets to S3, so the worker downloads audio without going through NAT. Its policy only allows the audio bucket and the bucket ECR images are pulled from.
    • One NAT, not two. Staging puts its only NAT in zone a to save about $37 a month. If zone a fails, both zones lose outbound internet. nat_per_az = true fixes that.
    • Optional private endpoints for SQS, Bedrock, Secrets Manager, ECR and logs cost money per zone, so they're off by default. NAT stays regardless, because Deepgram and Cognito's public keys are on the internet.
    data

    Data

    infra/modules/data/

    The three places the server keeps things, plus one encryption key for all of them. The names are a contract with the code. For example, the app is told STT_QUEUE=ernote-staging-jobs and works out the failure queue name itself by adding -dlq.

    PostgreSQL 16 (RDS)
    Every event, snapshot, transcript, chunk row and usage record. db.t4g.small, 50 GiB that can grow to 100. One zone in staging. Plaintext connections refused; the app verifies the server certificate.
    Backups
    Daily, kept 7 days in staging and can't be turned off. Deleting the database needs two deliberate changes, and a final snapshot is forced.
    Master password
    Created and stored by RDS in Secrets Manager. It never passes through Terraform, and it's used once to create the real app logins.
    S3 audio bucket
    ernote-staging-audio-000000000000-us-east-2. Never public, versioned, encrypted by default. Current files expire after 7 days, and replaced versions 7 days after they're replaced.
    SQS queue + DLQ
    ernote-staging-jobs and ernote-staging-jobs-dlq. Messages hold only IDs, never transcripts or names.
    Data KMS key
    Encrypts the database, its backups, audio and queue messages. Separate from the bootstrap key. Deleting it makes the data unrecoverable, so deletion waits 30 days.

    What happens to a job that keeps failing

    When the worker takes a job, the message is hidden from everyone else for 300 seconds. The worker renews that every 60 seconds while it works. If it crashes or gives up, the message reappears and another try starts.

    Try 1300 s lease, renewed every 60 s
    →
    Try 2message reappears after a failure
    →
    Try 3last attempt
    →
    Dead-letter queuekept 14 days, alarm fires

    The main queue keeps messages 4 days and the DLQ keeps them 14, so evidence of a failure outlives the work that caused it.

    identity

    Identity

    infra/modules/identity/

    Every program gets two roles. They all run from the same container image, but no two programs share a role.

    Execution role: the stagehand

    Used by ECS before the program starts. It pulls the image, injects that program's own secrets as environment variables, and writes to that program's own log group. Nothing else.

    Task role: the program's own badge

    Used by the running program for its AWS calls. Task roles can never read Secrets Manager. Secrets only arrive through injection at startup, so a bug in running code can't go fishing for other secrets.

    ProgramAccept audio uploadsRead audioSend jobsTake jobsCall BedrockLook up usersSecrets injected at start
    api✓ signs upload URLs✓ checks it arrived✓✗✗✗db/api
    worker✗✓ downloads✓✓✓ one approved model✗db/worker, deepgram
    migration✗✗✗✗✗✗db/migration
    onboarding✗✗✗✗✗✓ reads Cognito usersdb/onboarding
    db-bootstrapNo task role at all. It makes no AWS calls.all four DB logins + RDS master

    Denied for every program

    Each task role ends with a blanket Deny. No program can assume another role, change networks, IAM, the database server, queues or buckets, read Secrets Manager, or disable or delete a key. The db-bootstrap role is the only one that can read the master database credential.

    Five empty secret containers

    ernote-staging/db/api, /db/worker, /db/migration, /db/onboarding and ernote-staging/deepgram. Terraform creates the containers but never a value, so no password ever lands in Terraform state. There's no Anthropic key at all, because Bedrock uses the worker's role.

    GitHub deploy roles (optional, off)

    infrastructure
    State and plan files only. Creating foundation resources needs a separately reviewed policy, or a person using SSO.
    release
    Push images, register containers, update the two services, run only the migration task. Can't change networks, the database, IAM or secrets, and can't read audio or credentials.
    smoke
    Reads one synthetic login and one approved test WAV. Nothing else.

    GitHub can assume these only from this repository's protected environments. No role can hop into another role.

    sign-in

    Auth

    infra/modules/auth/

    One Cognito user pool and one app client per environment. The key idea: signing in proves who you are, and that's all. A successful login grants nothing. Which organization a clinician belongs to lives in the database's clinicians table, and only the er-onboard task can add someone there.

    The pool can't be deleted or replaced by accident. A new pool would give every user a new ID (sub) and orphan every clinician row.

    Off in staging until someone decides whether to import the existing sandbox pool or create a fresh one. Not wired into production yet.

    Self-signup
    Off. Only an admin can create users.
    Password reset
    Admin only. No email or SMS takeover path.
    MFA
    Required (authenticator app). Staging's labeled exception makes it optional for automated synthetic test users only.
    Client secret
    None. Phones can't keep secrets, so it uses the SRP password protocol instead.
    Tokens
    Access and ID tokens last 60 minutes, refresh tokens 12 hours. Refresh tokens can be revoked.
    Hosted login page
    Off unless exact callback URLs are given. No wildcards, no plain HTTP.
    compute

    Cluster

    infra/modules/cluster/

    Two long-lived things: an ECR image registry named ernote-staging, and a Fargate-only ECS cluster with the same name. Fargate means AWS runs the servers. You only describe containers.

    Image tags are immutable: once sha-3f8afd7… is pushed, nothing can push different bytes under that name. Every push is scanned for known vulnerabilities.

    Why only untagged images are ever deleted

    ECR's cleanup rules can't see which images are running. Any rule like "keep the last 50 tagged images" could eventually delete the running image or the one you'd roll back to. So the only rule deletes untagged images after 7 days, and Terraform refuses any rule that touches tagged ones. Tagged images pile up, and that storage cost is accepted.

    Builds must push a plain single-platform image, because the extra untagged pieces of a multi-platform build would match the cleanup rule.

    entry

    Edge

    infra/modules/edge/

    The front door. It needs a domain you already own in Route 53, such as api.staging.example.com. It creates:

    • An HTTPS certificate from ACM, proven by a DNS record.
    • An application load balancer in the public subnets. It accepts TLS 1.3 or 1.2 on port 443, drops malformed headers, and can't be deleted by accident.
    • A target group that sends traffic to API tasks on 8443 and checks /readyz every 15 seconds. Two failures take a task out and two passes put it back.
    • A DNS record pointing the name at the load balancer.
    • A WAF attached before the listener exists, so not even the first request skips it. If the load balancer can't reach the WAF, requests are refused rather than let through.

    Every request runs this list, top to bottom

    1. 0IngressClosedOnly present while ingress is off. Blocks every request.block all
    2. 5LabelSyncBodiesTags JSON POSTs to /v1/patients/{id}/events, which can be large.tag only
    3. 10AWS common rulesManaged protections against common attacks. Its 8 KiB body rule is set to count only.block
    4. 20Oversize bodiesBodies over 8 KiB are blocked, unless tagged as event sync.block
    5. 30Per-IP rateMore than 2,000 requests from one IP in 5 minutes.block
    6. endDefaultallow

    Manifest

    infra/modules/manifest/
    // s3://ernote-deploy-…/envs/staging/foundation-manifest.json (trimmed) { "schema_version": "1.0", "environment": "staging", "account_id": "000000000000", "region": "us-east-2", "resources": { "private_subnet_ids": "[\"subnet-0a1…\",\"subnet-0b2…\"]", "api_https_port": "8443", "audio_bucket": "ernote-staging-audio-000000000000-us-east-2", "stt_queue_name": "ernote-staging-jobs", "db_endpoint": "ernote-staging.c1x2y3.us-east-2.rds.amazonaws.com", "worker_task_role_arn": "arn:aws:iam::000000000000:role/ernote-staging-worker-task", "ecr_repository_url": "000000000000.dkr.ecr.us-east-2.amazonaws.com/ernote-staging", "cognito_pool_id": "us-east-2_AbC123xyz", "alarm_topic_arn": "arn:aws:sns:us-east-2:000000000000:ernote-staging-alarms", … up to 38 keys }, "secret_refs": { "worker_db": "arn:aws:secretsmanager:…:secret:ernote-staging/db/worker-Ab12Cd", "deepgram": "arn:aws:secretsmanager:…:secret:ernote-staging/deepgram-Xy34Zw" } }

    The foundation writes this file after everything it names has finished building. The bucket is versioned, so a release can pin the exact version it was reviewed against, and a later foundation change can't alter it.

    The release refuses a manifest when

    • its environment, account, region or project don't match
    • any required key is missing, which catches a half-finished foundation before it reaches ECS
    • a Cognito ID doesn't look like one from this region
    • anything under secret_refs isn't a Secrets Manager ARN. This is checked on the way out and on the way in, so a real password can't sneak through.

    The schema only allows text values, which is why the subnet list is stored as a JSON string and decoded on the other side.

    Applies to every container

    • Runs as a non-root user with a read-only filesystem.
    • No public IP, and remote shell access (ECS Exec) off.
    • If a new version keeps failing, ECS rolls back by itself (circuit breaker).
    • Old container definitions are kept, so a rollback can reuse them exactly.
    • Terraform never runs the migration itself. The pipeline does, before anything else changes.

    Where each value comes from

    The image is the ECR address from the manifest plus the digest from the pipeline. Plain settings like STT_QUEUE come straight from the manifest. Secrets appear only as pointers. ECS swaps in the real values as the container starts, using the worker's execution role, so the values never pass through Terraform, GitHub or the manifest.

    The API's container gets AUTH_MODE=cognito, the Cognito IDs, and API_TLS=self-signed. The migration gets only database settings.

    guards

    Encryption guards and account guards

    modules/s3-encryption-guards/ · guard.tf in every root

    Bucket encryption guards

    A shared set of bucket-policy rules used on the state, deploy and audio buckets. They refuse any upload that asks for the wrong encryption type, names a different key, asks for KMS without naming a key, or brings its own key (SSE-C). Uploads that don't mention encryption at all still work, because the bucket encrypts them by default. That matters for the phone's presigned uploads. These passed live signed tests on the bootstrap buckets on 2026-10-14.

    Wrong-account guards

    Every root refuses to run against the wrong AWS account, in two independent ways. The AWS provider is told the only allowed account ID. Separately, a check asks AWS who the current credentials belong to and fails the plan before anything is created if it doesn't match.

    The environment name (staging) is written into each root's code, not passed in, so you can't point a root at a different environment by changing a variable.

    Level 4 · putting it in motion

    How a deploy works

    When CI passes on master, .github/workflows/deploy.yml runs scripts/deploy.py. It writes a release record to the deploy bucket at every phase, so a retry or a rollback knows exactly where things stood. It has never run against AWS.

    Why "apply the saved plan" matters

    The plan made before the migration pins three things: the image digest, the manifest version, and the state it was planned against. Applying that same saved file means what was reviewed is exactly what runs. If anything changed in between, Terraform refuses the stale plan instead of quietly doing something different.

    Separate identities per job

    The deploy and accept jobs use the release role. The smoke test runs in its own GitHub environment with the smoke role, which can only read the synthetic test login and the test audio file. A smoke test can't change the deploy, and the deploy can't read the test credentials.

    Level 5 · how it gets turned on

    Everything starts switched off

    Each risky piece has a switch that defaults to off. Several switches refuse to turn on until an earlier one is on, and Terraform checks that during the plan. This is the order they'd be flipped for staging.

    1. infra/bootstrap appliedState and deploy buckets, key, five roles. Verified live on 2026-10-14.
      on
    2. staging/foundation appliedNetwork, database, bucket, queues, roles, cluster, logs. Needs: an approved budget, a chosen zone pair and address range.
      not applied
    3. auth.enabled = trueCreates the Cognito pool. Needs: a decision on importing the old sandbox pool or starting fresh.
      off
    4. edge = { hostname, hosted_zone_id }Certificate, load balancer, WAF, DNS. The WAF still blocks every request at this point. Needs: a domain you control.
      off
    5. telemetry.alarms_enabled = trueAlarm emails go out. Needs: a real delivery test.
      off
    6. edge.ingress_enabled = true + client_ipv4_cidrsRemoves the block-everything rule and opens port 443 to the listed IPs only. Terraform refuses unless alarms are on and the edge exists.
      off
    7. github_oidc_enabled + ciGitHub deploy roles. Needs: protected GitHub environments and checked subject strings.
      off
    8. services_enabled = true (release)The API and worker actually run. Terraform refuses unless the pinned manifest shows the alarm topic with notifications on, and an image digest and manifest version are given.

    Status and cost

    What exists in AWS today

    Only the bootstrap layer: two buckets, one key and five roles. Their storage, locking, recovery and role fences were checked live on 2026-10-14.

    What's been tested without AWS

    Every root validates, and the module tests run against a mocked AWS with no credentials (scripts/tf-network-check.sh, scripts/tf-data-check.sh and others). They check things like the address split, permission documents, WAF rules and the manifest guards. A mock can't prove that real AWS accepts a setting, though.

    docs/ops/step8-final-aws-live-checklist.md (2026-10-31) lists the remaining live steps in order: confirm the account and budget, set up GitHub trust, apply the foundation under SSO, then turn the switches above on one at a time with evidence recorded.

    Reference

    Jargon decoder

    TermPlain English
    TerraformA tool that reads text files describing cloud resources and makes the cloud match them.
    plan / applyA plan shows what would change, and apply does it. A saved plan can be applied later exactly as reviewed.
    state, backend, lockTerraform's record of what it built (state), where that record lives (backend: the S3 bucket), and the "in use" marker that stops two people changing it at once (lock).
    root, moduleA root is a folder you run Terraform in, with its own state. A module is a reusable building block that roots call.
    preconditionA rule in the code that fails the plan with a clear message if something isn't true yet.
    VPC, subnet, CIDRA private network, a slice of it, and the notation for an address range (10.40.0.0/16).
    availability zoneOne of several separate data centers in a region. Using two means one can fail.
    internet gateway, NATThe two-way door to the internet, and a one-way exit that lets private machines call out without being reachable.
    security groupA firewall attached to a component, listing who may connect to it and on which port.
    VPC endpointA private shortcut from the VPC to an AWS service that skips the internet.
    ALB, target groupThe load balancer that spreads incoming requests, and the list of tasks it sends them to.
    ACM, Route 53AWS's certificate service and DNS service.
    WAFA firewall that inspects each web request and blocks bad ones.
    ECS, FargateAWS's container runner, and the mode where AWS manages the servers underneath.
    task definition, serviceThe recipe for a container (image, size, settings), and the thing that keeps N copies of it running.
    ECR, digestThe image registry, and the fingerprint (sha256:…) that identifies an image's exact bytes.
    IAM role, policyAn identity a program can act as, and the written rules of what it may do.
    explicit denyA rule that says no. It always wins over any rule that says yes.
    task role vs execution roleThe running program's own permissions, versus the permissions ECS uses to start it (pull image, inject secrets, write logs).
    OIDCA way for GitHub Actions to prove who it is and get short-lived AWS credentials, so no stored keys are needed.
    KMS key, SSE-KMSAn encryption key AWS guards for you, and S3 encrypting stored files with it.
    presigned URLA temporary link that lets the phone upload one file directly to S3 using the API's permission.
    SQS, visibility timeout, DLQA job queue, how long a taken job stays hidden before it's retried, and the side queue where jobs go after repeated failure.
    RDS, Multi-AZAWS-managed PostgreSQL, and the option to keep a standby copy in a second zone (off in staging).
    Secrets ManagerEncrypted storage for passwords and API keys.
    Cognito user pool, subThe sign-in service and the permanent user ID it assigns.
    CloudWatch, CloudTrail, SNSLogs and alarms, the audit record of AWS actions, and the service that sends alert emails.
    Bedrock, inference profileAWS's way to call Claude, and a named route that may send requests to several US regions.
