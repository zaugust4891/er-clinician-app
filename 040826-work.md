## 1. Why StoredEvent Is Needed

The system has two fundamentally different concepts that are currently conflated:

**Domain eventsed ** (`NoteEvent`) represent *what happened* in the clinical domain: a clinician started recording, a transcript arrived, a result came in. These are pure domain concepts. They carry the data needto drive the state machine and populate the aggregate. They have no notion of persistence order, database identity, or wall-clock storage time.

**Persisted events** are what lives in the `events` table. Each row has a `sequence_id` (AUTOINCREMENT), an `occurred_at` timestamp, and a `payload` (the serialized `NoteEvent`). The database adds metadata that the domain event doesn't carry.

Right now, the Repository trait returns raw `NoteEvent` from `get_events()`:

```rust
// repository.rs:10 — current signature
fn get_events(&self, patient_id: PatientId) -> Vec<NoteEvent>
```

This throws away the `sequence_id` and `occurred_at` that the database recorded. The caller gets the event back but has lost the persistence metadata.

### The Snapshot Coordination Problem

The snapshot strategy (from the plan) is: save a snapshot at significant phase transitions, tagged with the `sequence_id` of the last event that was applied. On load, call `get_latest_snapshot(patient_id)` which returns `(sequence_id, PatientNote)`, then call `get_events_since(patient_id, sequence_id)` to get only the delta events.

The question is: **who knows the sequence_id to associate with the snapshot?**

The flow is:
1. `EventBus::publish()` calls `repo.append_event(patient_id, event)`
2. The event gets an AUTOINCREMENT `sequence_id` in SQLite
3. The caller applies the event to the in-memory `PatientNote`
4. If the note transitioned to Idle/Finalizing/Signed, call `repo.save_snapshot(patient_id, sequence_id, &note)`

Step 4 needs the `sequence_id` from step 2. 

Without `StoredEvent`, you'd have to either:
- Have `append_event` return `AppResult<u64>` (the sequence_id) — but then `get_events` still strips it, so replay can't correlate events with positions
- Track sequence_ids as a side-channel — fragile, error-prone, two sources of truth

`StoredEvent` solves this cleanly by bundling the persistence metadata with the domain event. Every caller that touches persisted events gets the full picture.

## 2. The StoredEvent Struct

```rust
pub struct StoredEvent {
    pub sequence_id: u64,
    pub event: NoteEvent,
    pub occurred_at: DateTime<Utc>,
}
```

Three fields. Each is load-bearing:

| Field | Type | Source | Why It Exists |
|-------|------|--------|---------------|
| `sequence_id` | `u64` | SQLite `AUTOINCREMENT` (`last_insert_rowid()`) | Total ordering of events per-database. Enables snapshot-delta coordination: "give me everything after position N." Also enables debugging: "what was the 47th thing that happened to this patient?" |
| `event` | `NoteEvent` | Deserialized from `payload TEXT` column | The actual domain event. This is what `apply_event()` and `replay()` operate on. Keeping it as a typed enum means callers pattern-match safely. |
| `occurred_at` | `DateTime<Utc>` | From `occurred_at TEXT` column (RFC 3339) | **The persistence timestamp** — when the event was written to SQLite. See [timestamp clarification](#timestamp-clarification-creative-improvement-1) below for how this interacts with clinical timestamps. |

**What it does NOT carry:**
- `patient_id` — the caller already knows this (they queried by it). Including it would be redundant.
- `event_type` — derivable from `event.event_type()`. No need to duplicate it.
- `payload` (raw JSON) — the struct exposes the deserialized `NoteEvent`, not the raw string. Callers work with types, not JSON.

**Derive traits:** `Debug, Clone`. NOT `Serialize/Deserialize` — `StoredEvent` is a read-side projection from the database, not something you serialize back. The database schema IS the serialization format.

### Timestamp Clarification (Creative Improvement #1)

`creative-improvements.md` recommends adding `occurred_at: DateTime<Utc>` to every `NoteEvent` variant as a *clinical timestamp* — when the thing actually happened in the real world. This creates a two-timestamp model:

| Timestamp | Lives On | Represents | Example |
|-----------|----------|------------|---------|
| `NoteEvent.occurred_at` | Domain event | When the clinical action happened | "Recording started at 14:32" |
| `StoredEvent.occurred_at` | Persistence wrapper | When the event was written to SQLite | "Persisted at 14:32.003" (same on first write, different on replay/migration) |

These are equal on first write and diverge on replay. On first write, `NoteEvent.occurred_at = Utc::now()` and `StoredEvent.occurred_at = Utc::now()` — they're milliseconds apart at most. But during replay, `NoteEvent.occurred_at` carries the original clinical time (preserved in the JSON payload), while `StoredEvent.occurred_at` reflects when the row was originally inserted (read from the database column).

**Impact on StoredEvent design:** No structural change to StoredEvent itself. The struct stays the same three fields. But its `occurred_at` field's *semantic contract* narrows: it is explicitly the persistence timestamp, not the clinical timestamp. During replay, `apply_event` should use `event.occurred_at` (clinical) for setting `Encounter.started_at`, NOT `stored_event.occurred_at` (persistence). This distinction must be clear in the code.

## 3. Repository Trait Changes

Side-by-side of every method, current vs. new:

### `append_event`

```
CURRENT:  fn append_event(&self, patient_id: PatientId, event: NoteEvent) -> AppResult<()>
NEW:      fn append_event(&self, patient_id: PatientId, event: NoteEvent) -> AppResult<u64>
```

**Why:** Returns the `sequence_id` assigned by SQLite. The caller (EventBus or snapshot trigger) needs this to know "I just persisted event #47." Implementation: `conn.last_insert_rowid() as u64`.

**Creative improvement #7 impact:** The returned `u64` becomes even more important because it feeds into the synchronous DashMap projection. The EventBus needs this value to coordinate snapshot-after-projection, not just snapshot-after-persist.

### `get_events`

```
CURRENT:  fn get_events(&self, patient_id: PatientId) -> Vec<NoteEvent>
NEW:      fn get_events(&self, patient_id: PatientId) -> AppResult<Vec<StoredEvent>>
```

**Two changes:**
1. Returns `Vec<StoredEvent>` instead of `Vec<NoteEvent>` — callers get sequence_id + occurred_at alongside each event
2. Returns `AppResult<...>` instead of bare `Vec` — database reads can fail (deserialization errors, SQLite errors). The current signature silently panics on errors (inside `todo!()`). The new signature makes errors explicit. For a medical app, swallowing database errors is unacceptable.

### `get_events_since`

```
CURRENT:  fn get_events_since(&self, patient_id: PatientId, sequence_id: u64) -> Vec<NoteEvent>
NEW:      fn get_events_since(&self, patient_id: PatientId, after_sequence_id: u64) -> AppResult<Vec<StoredEvent>>
```

Same two changes. The `after_sequence_id` parameter name clarifies semantics: `WHERE sequence_id > ?`. This is the method `load_patient_note` calls after loading a snapshot to get only the delta.

### `save_snapshot`

```
CURRENT:  fn save_snapshot(&self)                    // no params, no return
NEW:      fn save_snapshot(&self, patient_id: PatientId, sequence_id: u64, snapshot: &PatientNote) -> AppResult<()>
```

The current signature is a placeholder with no parameters. The real signature needs:
- `patient_id` — which patient's snapshot
- `sequence_id` — "this snapshot reflects state through event #N"
- `&PatientNote` — the aggregate to serialize via `serde_json::to_string()`

Implementation: `INSERT OR REPLACE INTO snapshots` — upsert semantics. One snapshot per patient. The latest always wins.

**Creative improvement #5 impact:** The implementation should also compute and store a SHA-256 checksum of the serialized snapshot JSON. See [snapshot integrity](#snapshot-integrity-creative-improvement-5) below.

### `get_latest_snapshot`

```
CURRENT:  fn get_snapshot(&self)                     // no params, no return
NEW:      fn get_latest_snapshot(&self, patient_id: PatientId) -> AppResult<Option<(u64, PatientNote)>>
```

Returns `Option` because a patient may have no snapshot (fresh start, full replay needed). The `u64` is the `sequence_id` at snapshot time — passed to `get_events_since()` for delta replay. The `PatientNote` comes back deserialized + `hydrate()`d.

**Creative improvement #5 impact:** Internally, this method should verify the snapshot checksum before returning. If the checksum doesn't match, return `Ok(None)` (not `Err`) — triggering full replay as a natural fallback. Log the corruption but don't block the clinician. See [snapshot integrity](#snapshot-integrity-creative-improvement-5).

### Default bodies: removed

```
CURRENT:  fn append_event(...) -> AppResult<()> { todo!() }   // has default
NEW:      fn append_event(...) -> AppResult<u64>;              // no default, required
```

Every method loses its `todo!()` default body. Without defaults, the compiler forces every implementor to provide real implementations. For a medical app, "compiles but panics" is worse than "doesn't compile."

## 4. Architectural Consistency

The architecture has four layers that events flow through. StoredEvent slots into a specific seam:

```
  Caller (audio pipeline, CLI)
       |
       v
  EventBus::publish(NoteEvent)          <-- domain event enters
       |
       +---> repo.append_event()        <-- persisted, gets sequence_id back (u64)
       |                                    StoredEvent is BORN here (conceptually)
       |
       +---> apply to DashMap           <-- synchronous projection (creative improvement #7)
       |
       +---> sender.send(event)         <-- broadcast for UI notifications (NOT state updates)
```

**On load (cold start or cache miss):**

```
  load_patient_note(repo, patient_id)
       |
       +---> repo.get_latest_snapshot()  <-- returns Option<(u64, PatientNote)>
       |                                    (returns None if checksum invalid - improvement #5)
       |
       +---> repo.get_events_since(seq)  <-- returns Vec<StoredEvent>
       |                                    HERE is where StoredEvent matters:
       |                                    caller gets sequence_ids for each event
       |
       +---> for stored in events {
                apply_event(&mut note, &stored.event)  <-- uses .event field
                // uses event.occurred_at for clinical timestamps (improvement #1)
             }
             // last stored.sequence_id = new snapshot position
```

### Key Architectural Points

**StoredEvent is a read-side concept.** It doesn't change how events are published or how the state machine works. `NoteEvent` remains the domain currency — the thing that `apply_event()` pattern-matches on, the thing callers construct. `StoredEvent` only appears when you *read events back from the database*.

**StoredEvent lives in `repository.rs`, not `events.rs`.** It's a persistence concern, not a domain concern.

**Consistency with persist-first.** `EventBus::publish()` already calls `repo.append_event()` BEFORE `sender.send()`. StoredEvent doesn't change this flow. It only changes the return type of `append_event` from `()` to `u64`.

**Consistency with DashMap projection.** The DashMap stores `PatientNote`, not `StoredEvent`. Events flow through the store as `NoteEvent` via the broadcast channel (or via direct synchronous projection per creative improvement #7). StoredEvent is only relevant on the persistence/reload path.

### Updated EventBus Flow (Creative Improvement #7)

The original design has broadcast subscribers updating the DashMap. Creative improvement #7 identifies a race condition: nothing guarantees the DashMap stays in sync with SQLite during normal operation. The fix makes DashMap update *part of* the persist-then-project flow:

```rust
pub fn publish(&self, event: NoteEvent, store: &PatientNoteStore) -> AppResult<u64> {
    // 1. Persist (returns sequence_id via StoredEvent-enabled trait)
    let seq_id = if let Some(repo) = &self.repository {
        repo.append_event(event.extract_patient_id(), event.clone())?
    } else {
        0
    };

    // 2. Update in-memory projection synchronously
    let patient_id = event.extract_patient_id();
    store.entry(patient_id)
        .and_modify(|note| apply_event(note, &event))
        .or_insert_with(|| {
            let mut note = PatientNote::new(patient_id);
            apply_event(&mut note, &event);
            note
        });

    // 3. Broadcast (notifications only, NOT state updates)
    let _ = self.sender.send(event);
    Ok(seq_id)
}
```

**Impact:** `publish()` now returns `AppResult<u64>` instead of `AppResult<()>`. The sequence_id flows up to the caller, enabling snapshot coordination at the call site. This signature change is a direct consequence of StoredEvent.

**Trade-off:** This couples EventBus to PatientNoteStore. If you want to decouple them later, extract a `Projector` trait. But for a single-device app with one SQLite file, the coupling is justified by the consistency guarantee.

## 6. Production-Grade Considerations

This is a real app for ER doctors during patient encounters. StoredEvent's design reflects that.

### Crash Safety

`append_event` returns `u64` only after the SQLite INSERT commits (WAL mode ensures durability). If the process crashes between `append_event` and `sender.send()`, the event is persisted but not broadcast. On restart, `load_patient_note` replays from the event log — no data loss. StoredEvent's `sequence_id` is what makes this recovery path work: the snapshot knows "I'm at position 47," and `get_events_since(47)` picks up exactly where it left off. No gaps, no duplicates.

### Data Integrity

`sequence_id` is a monotonically increasing, gap-free integer (SQLite AUTOINCREMENT). This gives a total order guarantee per-database. If you ever see sequence_ids 1, 2, 4 (missing 3), something is catastrophically wrong — a row was deleted from an append-only log. This is easy to detect and should trigger an alert.

### Snapshot Integrity (Creative Improvement #5)

Snapshots are a performance optimization, not a source of truth — but a corrupted snapshot that fails to deserialize would block `load_patient_note` if not handled. The fix:

- **On save:** Compute SHA-256 of the serialized JSON, store in `checksum` column
- **On load:** Verify hash before deserializing. If mismatch, log the corruption and return `Ok(None)` — triggering full replay from the event stream as a natural fallback
- **Cost:** ~5 lines in `save_snapshot` (compute hash), ~3 lines in `get_latest_snapshot` (verify hash). Small investment, critical safety net.

The clinician never sees this. If a snapshot is corrupt, load takes microseconds longer (full replay of 20-50 events). The event stream is the source of truth; the snapshot is a cache.

### Timestamp Fidelity (Creative Improvement #1)

Two-timestamp model:

- `NoteEvent.occurred_at` = clinical time (when the doctor started recording). Carried in the event payload, preserved through serialization, used during replay for `Encounter.started_at`.
- `StoredEvent.occurred_at` = persistence time (when the row was written). Read from the database column, useful for auditing the persistence layer itself.

For a medical-legal document, clinical timestamps must be accurate. `apply_event` must use the event's `occurred_at`, not `Utc::now()` during replay, and not `StoredEvent.occurred_at`. This is the distinction that creative improvement #1 establishes, and it requires StoredEvent to exist as a separate concept to make the boundary clear.

### Event Compaction Future-Proofing (Creative Improvement #4)

After a note is signed and the retention period expires, raw transcripts (PHI) should be compactable. The compaction mechanism references events by their `sequence_id`:

```rust
TranscriptCompacted {
    patient_id: PatientId,
    encounter_id: Uuid,
    original_sequence_id: u64,  // <-- THIS is a StoredEvent.sequence_id
    summary_hash: String,
    compacted_at: DateTime<Utc>,
}
```

Without StoredEvent making sequence_ids visible to callers, compaction can't reference the original event. This is a future concern, but it validates that StoredEvent's design is correct — the sequence_id isn't just for snapshots, it's the universal coordinate system for the event stream.

### Schema Evolution

Once events are in production, `NoteEvent` can't change shape freely. Adding a field to `AudioStarted` would break deserialization of old events. `StoredEvent.sequence_id` enables migration strategies: "for all events with sequence_id < 5000, use deserializer v1; after that, use v2." The sequence_id is the versioning coordinate.

### Replay Idempotency

State-transition events are idempotent via the state machine's no-op default. Data events (ResultReceived) are NOT — replaying one twice pushes duplicate results. In append-only SQLite on a single device, duplicates can't occur. But `sequence_id` gives a detection mechanism if ever needed.

### Auditability

Medical records require knowing *what happened, when, and in what order*. StoredEvent gives all three: `event` (what), `occurred_at` (when), `sequence_id` (order). An auditor asking "show me everything that happened to patient X in chronological order with timestamps" gets answered directly from `Vec<StoredEvent>`.

## 7. Creative Improvements Impact Analysis

Cross-reference of all 7 creative improvements against the StoredEvent/Repository implementation.

### Impact Summary

| # | Improvement | Urgency | Impact Level | Changes Required |
|---|---|---|---|---|
| 1 | Clinical timestamps in events | NOW | **DIRECT** | Clarifies `StoredEvent.occurred_at` semantic contract. `apply_event` uses `event.occurred_at`, not `stored.occurred_at`. |
| 2 | Command/fact event separation | NOW | INDIRECT | More event variants flow through same StoredEvent pipeline. No structural change. |
| 3 | Addendum problem | BEFORE PROD | INDIRECT | New event variants, same pipeline. Raises replay question for rejected events. |
| 4 | Event compaction for PHI | BEFORE PROD | **DIRECT** | Validates sequence_id visibility is essential (compaction references it). |
| 5 | Snapshot integrity verification | NOW | **DIRECT** | Adds checksum to snapshots table. Changes `get_latest_snapshot` behavior. |
| 6 | Replay validation event | FUTURE | INDIRECT | `ReplayResult.final_sequence_id` comes from StoredEvent. No structural change. |
| 7 | DashMap race condition | NOW | **DIRECT** | `append_event`'s returned `u64` feeds DashMap projection. `publish()` signature changes. |

### Detail: Improvement #1 — Clinical Timestamps

**What changes:** Nothing in `StoredEvent` structurally. But its `occurred_at` field's semantic contract narrows from "when the event happened" to "when the event was persisted." The domain event carries its own `occurred_at` for clinical timing.

**Implementation note:** When `NoteEvent` variants get their `occurred_at` field (Phase 1 of the plan adds `encounter_id` to AudioStarted — this field should be added at the same time), the `apply_event` function must use `event.occurred_at` for domain timestamps:

```rust
// In apply_event:
NoteEvent::AudioStarted { encounter_id, occurred_at, .. } => {
    let encounter = Encounter {
        id: *encounter_id,
        started_at: *occurred_at,  // clinical time, NOT Utc::now()
        // ...
    };
}
```

### Detail: Improvement #5 — Snapshot Integrity

**What changes:**

1. `db.rs` schema — add `checksum TEXT NOT NULL` to snapshots table
2. `save_snapshot` implementation — compute SHA-256 of serialized JSON before INSERT
3. `get_latest_snapshot` implementation — verify checksum on read, return `None` on mismatch

**Dependencies:** Requires `sha2` crate in Cargo.toml (or use a simpler hash if SHA-256 is overkill for single-device integrity checking).

**Why this belongs in the StoredEvent phase:** The `save_snapshot` and `get_latest_snapshot` methods are being rewritten as part of the Repository trait redesign. Adding the checksum now is ~8 lines of extra code during a method that's being rewritten anyway. Adding it later means modifying methods that are already tested and working.

### Detail: Improvement #7 — DashMap Synchronous Projection

**What changes:**

1. `EventBus::publish()` signature gains `store: &PatientNoteStore` parameter and returns `AppResult<u64>` instead of `AppResult<()>`
2. The `EventBus` struct may gain a `store: PatientNoteStore` field (or take it as a parameter)
3. `apply_event` from `state.rs` must be callable from `events.rs` (may need to be `pub`)
4. Broadcast subscribers no longer update the DashMap — they're for UI notifications, logging, etc.

**Trade-off:** Couples EventBus to PatientNoteStore. Acceptable for a single-device app. Decoupling via a `Projector` trait is a future option.

**Dependencies:** `apply_event` must exist before this can be wired (Phase 4 of the plan). So the DashMap sync wiring happens after the core StoredEvent + Repository + replay work is done.

### Improvements That DON'T Affect StoredEvent

**#2 (Command/fact separation):** A design decision about NoteEvent's shape. Whether you have 7 variants or 11, they all flow through `StoredEvent` the same way. The Repository trait doesn't care about variant count.

**#3 (Addendum problem):** A state machine concern. If `AddendumAdded` events are introduced, they're just new NoteEvent variants. StoredEvent wraps them identically. The question of "what happens when replay encounters events the state machine rejects" is a replay logic concern, not a StoredEvent concern.

**#6 (Replay validation):** A consumer of StoredEvent data (`final_sequence_id`), not a change to StoredEvent itself. This is a state.rs concern for when replay is implemented.

### Pre-Change Repository Trait (`src/repository.rs`)
