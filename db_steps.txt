DB Repository Layer: Step-by-Step Guide                                      
                                                                          
  Overview: What You're Building                                          
                                                                          
  The repository layer sits between your domain models (models/) and the raw   
  SQLite database (db.rs). Its job is to translate between Rust structs and SQL
   rows. Right now db.rs creates the tables but has no code to read or write
  data.                                  
                                                                               
  You'll add a new file src/repository.rs (and register it in lib.rs)          
  containing functions that accept a &Connection and operate on your domain    
  types.                                                                       

  ---
  Step 1: Understand the Serialization Strategy

  Your schema uses two patterns for storing data. Understanding this split is
  critical before writing any code.

  Pattern A — Columnar storage (for fields you query/filter on):
  encounters table:
    id, patient_id, capture_mode, started_at, ended_at, transcript,
  encounter_number
  Each field is its own column. You can WHERE patient_id = ? or ORDER BY
  started_at.

  Pattern B — JSON blob storage (for complex nested data):
  patients table:
    id, shift_id, chief_complaint, room, data TEXT
  The data column holds the full PatientRecord serialized as JSON via
  serde_json::to_string(). This avoids needing a column for every field (like
  first_name, last_name, age) and makes schema evolution easy — you add a field
   to the struct and existing rows just deserialize with None/defaults.

  When to use which:
  - If you need to query/filter/sort by a field → make it a column
  - If it's just stored and retrieved as a unit → put it in the JSON blob
  - Some fields appear in BOTH places (like chief_complaint is a column AND
  inside the JSON data blob) — the column is for queries, the blob is for full
  deserialization

  Look at each table in your db.rs schema and identify which pattern it uses.
  The encounters table is fully columnar. The patients and results tables are
  hybrid (some columns + a JSON data blob). The shifts table uses a JSON blob
  for the full struct.

  ---
  Step 2: Create the Repository File

  Create src/repository.rs and add pub mod repository; to src/lib.rs.

  Start with the imports you'll need:

  use rusqlite::{params, Connection};
  use crate::error::Result;
  use crate::models::*;  // all your domain types

  The params! macro from rusqlite is how you pass bind parameters to SQL
  statements. It converts Rust types into SQLite-compatible values. For
  example:

  conn.execute(
      "INSERT INTO shifts (id, started_at, data) VALUES (?1, ?2, ?3)",
      params![shift_id_string, started_at_string, json_string],
  )?;

  The ?1, ?2, ?3 are positional placeholders. params! fills them in order. This
   prevents SQL injection — never use format!() to build SQL.

  ---
  Step 3: Implement Shift CRUD

  Start with Shift because it's the simplest and the top-level container.

  save_shift:
  - Take &Connection and &Shift
  - Serialize the Shift to JSON with serde_json::to_string()
  - Convert shift.id to a String with .to_string() (UUIDs go into TEXT columns)
  - Convert shift.started_at to an RFC 3339 string with .to_rfc3339() (chrono's
   DateTime<Utc> has this method — SQLite stores dates as TEXT)
  - Convert shift.ended_at the same way, but it's an Option — for None, pass
  rusqlite::types::Null or use .map(|dt| dt.to_rfc3339())
  - Execute an INSERT OR REPLACE INTO shifts statement

  get_shift:
  - Take &Connection and a ShiftId
  - Execute SELECT data FROM shifts WHERE id = ?1
  - Use conn.query_row() which returns exactly one row or an error
  - Deserialize the JSON data column back into a Shift with
  serde_json::from_str()

  get_active_shift:
  - SELECT data FROM shifts WHERE ended_at IS NULL ORDER BY started_at DESC
  LIMIT 1
  - Use conn.query_row() — if no active shift exists, return Ok(None) instead
  of an error. Use conn.query_row().optional() (the optional() method on
  rusqlite's Result converts a "no rows" error into Ok(None))

  Important rusqlite pattern — optional():
  use rusqlite::OptionalExtension;  // this trait adds .optional()

  let result: Option<Shift> = conn
      .query_row("SELECT data FROM shifts WHERE id = ?1", params![id], |row| {
          let json: String = row.get(0)?;
          Ok(serde_json::from_str(&json).unwrap())  // handle this error
  properly
      })
      .optional()?;

  The row.get(0)? extracts column 0 from the result row. The closure maps each
  row to your Rust type.

  ---
  Step 4: Implement Patient CRUD

  save_patient:
  - Takes &Connection, a ShiftId, and a &PatientRecord
  - Serialize the full PatientRecord as JSON for the data column
  - Also extract chief_complaint and room as individual column values (for
  querying)
  - INSERT OR REPLACE INTO patients (id, shift_id, chief_complaint, room, data)
   VALUES (?1, ?2, ?3, ?4, ?5)

  get_patient:
  - SELECT data FROM patients WHERE id = ?1
  - Deserialize JSON back to PatientRecord

  list_patients_for_shift:
  - This returns multiple rows, so you use conn.prepare() + stmt.query_map()
  instead of query_row()
  - The pattern:

  let mut stmt = conn.prepare("SELECT data FROM patients WHERE shift_id =
  ?1")?;
  let rows = stmt.query_map(params![shift_id.to_string()], |row| {
      let json: String = row.get(0)?;
      Ok(json)
  })?;

  let mut patients = Vec::new();
  for row in rows {
      let json = row?;
      let patient: PatientRecord = serde_json::from_str(&json)
          .map_err(|e| /* convert to your AppError */)?;
      patients.push(patient);
  }
  Ok(patients)

  The query_map returns an iterator of Result<T> — each row might fail to
  extract, so you need to handle errors inside the loop. The ? inside for row
  in rows unwraps each row result.

  Gotcha with rusqlite error conversion: query_map's closure returns
  rusqlite::Result, but serde_json::from_str returns a serde_json::Error. You
  can't use ? directly inside the closure to convert between them. Two options:
  1. Use .unwrap() inside the closure (acceptable for a known-good schema)
  2. Map the serde error to rusqlite::Error::ToSqlConversionFailure manually

  For the MVP, option 1 is pragmatic. If the JSON in the database can't
  deserialize to your struct, something is deeply wrong and panicking is
  reasonable.

  ---
  Step 5: Implement Encounter CRUD

  Encounters are fully columnar (no JSON blob), so the mapping is more
  explicit.

  save_encounter:
  INSERT OR REPLACE INTO encounters
    (id, patient_id, capture_mode, started_at, ended_at, transcript,
  encounter_number)
  VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7)

  For capture_mode, you need to convert the CaptureMode enum to a string. Add a
   simple method or use serde_json::to_string() — but for a columnar field, a
  plain match is clearer:

  let mode_str = match encounter.capture_mode {
      CaptureMode::Ambient => "ambient",
      CaptureMode::Dictation => "dictation",
  };

  And the reverse when reading:
  let mode: CaptureMode = match mode_str.as_str() {
      "ambient" => CaptureMode::Ambient,
      "dictation" => CaptureMode::Dictation,
      other => return Err(/* unknown capture mode */),
  };

  get_encounters_for_patient:
  - SELECT * FROM encounters WHERE patient_id = ?1 ORDER BY started_at ASC
  - Map each row column-by-column back into an Encounter struct
  - For ended_at and transcript, these are Option fields — use row.get::<_,
  Option<String>>(4)? to handle nullable columns

  The row.get type annotation pattern:
  let id: String = row.get(0)?;
  let patient_id: String = row.get(1)?;
  let capture_mode: String = row.get(2)?;
  let started_at: String = row.get(3)?;
  let ended_at: Option<String> = row.get(4)?;
  let transcript: Option<String> = row.get(5)?;
  let encounter_number: i64 = row.get(6)?;  // SQLite integers are i64

  Then you need to parse strings back into your types:
  - UUID: Uuid::parse_str(&id)? — add uuid to your error type or map it
  - DateTime: DateTime::parse_from_rfc3339(&started_at)?.with_timezone(&Utc) —
  chrono provides this

  ---
  Step 6: Implement Results CRUD

  Results use the hybrid pattern: columnar fields for querying + JSON blob for
  the full ClinicalResult.

  save_result:
  - Extract id, patient_id, source (as string), timestamp as columns
  - Serialize the entire ClinicalResult as JSON for the data column
  - INSERT INTO results (id, patient_id, source, timestamp, data) VALUES (?1,
  ?2, ?3, ?4, ?5)

  For ResultSource → string conversion:
  let source_str = match result.source {
      ResultSource::Manual => "manual",
      ResultSource::FhirPull => "fhir_pull",
      ResultSource::Hl7Feed => "hl7_feed",
  };

  get_results_for_patient:
  - SELECT data FROM results WHERE patient_id = ?1 ORDER BY timestamp ASC
  - Deserialize each row's JSON data column back to ClinicalResult

  ---
  Step 7: Implement Note Sections CRUD

  Note sections are versioned — you never update, you always insert a new
  version. This is the append-only pattern from the architecture.

  save_note_section_version:
  - Takes a patient_id, section name ("hpi", "exam", "mdm"), content string,
  version number, and source encounter IDs
  - INSERT INTO note_sections (patient_id, section, content, version,
  generated_at, source_encounter_ids) VALUES (?1, ?2, ?3, ?4, ?5, ?6)
  - The source_encounter_ids field is a Vec<Uuid> — serialize it as a JSON
  array string

  get_latest_sections:
  - This is the trickiest query. You need the latest version of each section
  type for a patient:
  SELECT section, content FROM note_sections
  WHERE patient_id = ?1
  AND version = (
      SELECT MAX(version) FROM note_sections ns2
      WHERE ns2.patient_id = note_sections.patient_id
      AND ns2.section = note_sections.section
  )
  - Map the results into a NoteSections struct by matching on the section
  string ("hpi" → sections.hpi = Some(content), etc.)

  get_section_history:
  - SELECT * FROM note_sections WHERE patient_id = ?1 AND section = ?2 ORDER BY
   version ASC
  - Returns Vec<NoteSectionVersion> — useful for the audit trail and showing
  how a section evolved

  ---
  Step 8: Implement Audit Log

  The audit log is append-only. No updates, no deletes.

  append_audit_entry:
  - INSERT INTO audit_log (id, patient_id, timestamp, action, details) VALUES
  (?1, ?2, ?3, ?4, ?5)
  - Serialize AuditAction to a string (use serde_json::to_string() for the enum
   — this gives you {"PhaseTransition":{"from":"Idle","to":"Encountering"}}
  which is self-describing and easy to deserialize later)
  - patient_id is Option<String> — some audit events are shift-level, not
  patient-level

  get_audit_log:
  - SELECT * FROM audit_log ORDER BY timestamp ASC
  - Optional filter: WHERE patient_id = ?1 for patient-specific logs
  - Optional filter: WHERE timestamp > ?1 for recent entries

  ---
  Step 9: Write Tests

  For each repository function, write at least one test. The pattern is always
  the same:

  #[cfg(test)]
  mod tests {
      use super::*;
      use crate::db::open_memory_db;

      #[test]
      fn test_save_and_get_shift() {
          let conn = open_memory_db().unwrap();
          let shift = Shift::new();

          save_shift(&conn, &shift).unwrap();
          let loaded = get_shift(&conn, shift.id).unwrap();

          assert_eq!(loaded.id, shift.id);
          assert!(loaded.is_active());
      }
  }

  The in-memory DB from open_memory_db() gives you a fresh database per test —
  no cleanup needed, no file system side effects.

  Tests to write (minimum):
  1. Save and retrieve a shift
  2. Save patient, list patients for shift, get patient by ID
  3. Save two encounters for the same patient, retrieve in order
  4. Save a lab result, retrieve it
  5. Save two versions of HPI, verify get_latest_sections returns the newest
  6. Append audit entries, retrieve in order
  7. Round-trip test: save a complex ClinicalResult with a LabResult inside,
  verify all fields survive JSON serialization

  ---
  Step 10: Register the Module

  Add to src/lib.rs:
  pub mod repository;

  Then in main.rs, you can smoke-test the full round trip:
  - Create a shift, save it
  - Create a patient, save it
  - Create an encounter, save it
  - Query it all back and log it

  ---
  Common Pitfalls to Watch For

  1. UUID ↔ String: rusqlite doesn't natively understand Uuid. Always
  .to_string() before inserting and Uuid::parse_str() when reading back.
  2. DateTime ↔ String: Same thing. Use .to_rfc3339() for writing and
  DateTime::parse_from_rfc3339() for reading. Chrono's NaiveDateTime won't work
   — always use DateTime<Utc>.
  3. Option columns: When a column is nullable in SQLite, use row.get::<_,
  Option<String>>(n)? — not row.get::<_, String>(n)? which will panic on NULL.
  4. INSERT OR REPLACE vs INSERT: Use OR REPLACE for entities that get updated
  (shifts, patients). Use plain INSERT for append-only data (audit log, note
  section versions).
  5. Transaction batching: If you're saving a patient + their first encounter +
   an audit entry all at once, wrap them in a transaction:
  let tx = conn.transaction()?;
  save_patient(&tx, shift_id, &patient)?;
  save_encounter(&tx, &encounter)?;
  append_audit_entry(&tx, &entry)?;
  tx.commit()?;
  5. Connection::transaction() returns a Transaction that derefs to Connection,
   so all your functions work with it unchanged. If anything fails, the whole
  batch rolls back.
  6. The rusqlite::OptionalExtension trait: You must use
  rusqlite::OptionalExtension; to get the .optional() method on query results.
  This is easy to forget and gives a confusing compiler error.

  ---
  That should give you everything you need to build the full repository layer.
  The total is roughly 6-8 functions with matching tests, around 300-400 lines
  of code. Start with shifts (simplest), work up to note sections (most complex
   query), and save audit log for last (trivial once you've done the rest).
